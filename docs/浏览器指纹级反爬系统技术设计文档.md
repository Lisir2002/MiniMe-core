## 1. 文档概述

### 1.1 背景

MiniMe-core 的内置浏览器是 AI Agent 的核心工具之一，模型通过 browser 工具完成网页导航、数据抓取、表单填写、自动化操作等任务。随着目标网站反爬技术的升级，传统的"操作行为模拟"（safe_click/human_type）已不足以应对指纹级反爬检测。

当前面临的核心问题：
- **浏览器指纹暴露**：WebView 环境的真实指纹（Canvas/WebGL/Audio/UA 等）可被网站稳定识别和追踪
- **多任务关联**：不同 AI 任务共享同一浏览器环境，容易被网站关联为同一用户
- **反爬响应被动**：被检测后只能靠模型"瞎试"，没有系统化的应对策略
- **模型能力缺失**：模型不知道有指纹配置能力，也不会主动使用，指纹功能成为"哑巴功能"

### 1.2 目标

构建一套完整的**浏览器指纹级反爬系统**，实现以下目标：

| 目标层级 | 具体目标 | 衡量标准 |
|---------|---------|---------|
| **基础目标** | 实现主流浏览器指纹的随机化/伪装 | Canvas/WebGL/Audio/UA 等 10+ 指纹项可配置 |
| **功能目标** | 模型可通过工具接口感知、配置、检测、调整指纹 | 20+ 个指纹/反爬工具动作可用 |
| **效果目标** | 显著降低被反爬检测的概率 | CreepJS 评分 > 80，FingerprintJS 无法稳定识别 |
| **智能目标** | AI 驱动的反爬策略，自动识别反爬模式并生成最优应对 | 反爬场景下自动响应成功率 > 80% |
| **体验目标** | 用户无感知，模型自动处理，不影响正常使用 | 页面加载延迟增加 < 100ms，操作流畅 |

### 1.3 范围

**包含**：
- 浏览器侧指纹伪装（Canvas/WebGL/Audio/字体/UA/WebRTC 等）
- 指纹配置文件管理（创建/保存/切换/删除/导入导出）
- 模型交互接口（fingerprint_* / antidetect_* / browser_* 工具动作）
- 反爬状态感知与自适应控制
- AI 驱动的反爬策略（感知层/决策层/学习层）
- 与现有 browser 工具的深度集成

**不包含**：
- 独立 Chromium 内核（当前基于系统 WebView）
- 云端指纹池（当前本地存储）
- 多设备同步（当前单设备）
- 针对特定网站的攻击模式（遵守 robots.txt 和使用边界）

### 1.4 术语表

| 术语 | 说明 |
|------|------|
| 浏览器指纹 | 通过浏览器 API 获取的可唯一标识设备/浏览器的特征集合 |
| Canvas 指纹 | 通过 Canvas 2D API 渲染图形并读取像素值生成的指纹 |
| WebGL 指纹 | 通过 WebGL API 获取的显卡/渲染器信息生成的指纹 |
| Audio 指纹 | 通过 Web Audio API 分析音频处理管线特征生成的指纹 |
| 指纹配置文件 | 一组内部一致的指纹参数集合，可整体切换 |
| 一致性校验 | 检查指纹配置内部各参数是否匹配（如 UA 与 platform、时区与语言） |
| 反爬信号 | 网站反爬系统触发的可观测事件（验证码、403、拦截页等） |
| 自适应调整 | 根据反爬信号自动调整指纹/代理/操作节奏的机制 |
| 上下文老虎机 | 一种强化学习算法，根据上下文状态选择期望收益最高的动作 |
| 概念漂移 | 反爬系统的模式随时间变化，导致原有策略失效 |

#### 2.3.1 指纹应用流程

```
模型调用 fingerprint_set(profile_id="xxx")
    │
    ▼
FingerprintManager 加载配置
    │
    ▼
FingerprintValidator 一致性校验
    │── 不通过 ──▶ 返回错误 + 修正建议
    │
    ▼ 通过

    │
    ▼

    │
    ▼
页面加载 → 脚本先于页面 JS 执行 → 指纹伪装生效
    │
    ▼
返回成功 + 当前指纹摘要
```

```
浏览器操作执行
    │
    ▼

    │── 无信号 ──▶ 正常返回
    │
    ▼ 检测到信号

    │
    ▼
AI 策略引擎感知当前状态（50+ 特征）
    │
    ▼
AI 模型推荐最优动作（切换指纹/代理/降低频率等）
    │
    ▼
规则兜底层校验（不犯傻：不能同时做高风险组合）
    │
    ▼
执行调整动作
    │
    ▼
记录调整结果 → 反馈给 AI 模型 → 更新参数
    │
    ▼
返回调整结果给模型（包含新状态、建议后续操作）
```

```

    │
    ▼

    │
    ▼

    ▼

    │
    ▼

    │
    ▼

    │
    ▼

    │
    ▼
```

### 3.2 Canvas 指纹随机化设计

#### 3.2.1 噪声算法

```
算法：高斯分布像素噪声
输入：原始像素数据 (R, G, B, A)
输出：噪声处理后的像素数据

对于每个像素的每个通道（R/G/B）：
    noise = gaussian_random(mean=0, std=1.5)  // 高斯分布，标准差1.5
    new_value = clamp(original + noise, 0, 255)
Alpha 通道不处理（保持透明信息）

优化：
    - 大画布（> 100万像素）分块处理，每块 256x256
    - 同一画布多次 toDataURL 使用相同噪声种子（避免闪烁）
    - 噪声种子与指纹配置绑定（同一指纹产生一致的噪声模式）
```

```javascript
    const FAKE_VENDOR = '__WEBGL_VENDOR__';
    const FAKE_RENDERER = '__WEBGL_RENDERER__';

    // UNMASKED_VENDOR_WEBGL = 37445
    // UNMASKED_RENDERER_WEBGL = 37446

    function patchGetParameter(glProto) {
        const originalGetParameter = glProto.getParameter;
        glProto.getParameter = function(parameter) {
            if (parameter === 37445) return FAKE_VENDOR;
            if (parameter === 37446) return FAKE_RENDERER;
            return originalGetParameter.call(this, parameter);
        };
        glProto.getParameter.toString = function() {
            return 'function getParameter() { [native code] }';
        };
    }

    // 同时 patch WebGL 和 WebGL2
    patchGetParameter(WebGLRenderingContext.prototype);
    patchGetParameter(WebGL2RenderingContext.prototype);
})();
```

### 3.4 Audio 指纹伪装设计

#### 3.4.1 频域噪声算法

```
算法：高频微扰
输入：getByteFrequencyData 返回的 Uint8Array（频域数据）
输出：添加噪声后的频域数据

对于每个频率点 i：
    if i > 128 (高频区域，人耳不敏感):
        noise = random(-2, 2)  // ±2 的微小扰动
        data[i] = clamp(data[i] + noise, 0, 255)
    else (低频区域，保持不变):
        不处理

优化：
    - 只处理高频，不影响正常音频播放质量
    - 噪声模式与指纹配置绑定
    - getFloatFrequencyData 类似处理（浮点精度）
```

### 3.6 WebRTC 防护设计

```javascript
// webrtc_protection.js
(function() {
    'use strict';

    // 重写 RTCPeerConnection，阻止 ICE candidate 收集
    const originalRTCPeerConnection = window.RTCPeerConnection;
    window.RTCPeerConnection = function(configuration) {
        const pc = new originalRTCPeerConnection(configuration);

        // 拦截 onicecandidate，不返回真实 candidate
        Object.defineProperty(pc, 'onicecandidate', {
            set: function(handler) {
                this._onicecandidate = function(event) {
                    // 不传递真实 candidate，传递 null（表示收集完成）
                    if (event.candidate) {
                        return;  // 丢弃所有 candidate
                    }
                    handler.call(this, event);
                };
            },
            get: function() {
                return this._onicecandidate;
            }
        });

        return pc;
    };
```

### 3.7 注入时机与合并策略

#### 3.7.1 注入时机

| 注入方式 | 时机 | 适用场景 |
|---------|------|---------|
| `shouldInterceptRequest` 拦截 HTML | 在 `<head>` 首行注入 `<script>` | 主页面，最优先 |
| `WebViewClient.onPageStarted` + `evaluateJavascript` | 页面开始加载时 | 备用方案，可能略晚 |
| `WebViewClient.onPageFinished` | 页面加载完成后 | 不适用（太晚了，页面已获取真实指纹） |

#### 3.7.2 脚本合并

所有指纹注入脚本合并为一个脚本，减少注入次数：


## 4. 模型交互接口设计

### 4.1 接口设计原则

1. **动作语义清晰**：每个动作名直接表达功能，模型一看就懂
2. **参数最小化**：必填参数尽量少，可选参数有合理默认值
3. **返回结构化**：返回统一的 envelope 结构，包含 ok/error/error_code/data/summary/note
4. **错误码驱动**：模型可根据 error_code 做决策，不需要解析自然语言错误
5. **场景引导完整**：description 中明确说明每个动作的使用场景、调用时机、注意事项

### 4.2 统一返回结构（Envelope）

```json
{
  "ok": true,
  "action": "fingerprint_set",
  "summary": "已切换到美国 Chrome 指纹（评分 85）",
  "error": null,
  "error_code": null,
  "data": {
    "profile_id": "fp_001",
    "profile_name": "US Chrome High-End",
```

## 5. AI 驱动反爬策略设计

### 5.1 设计理念

传统规则引擎的局限性：
- 规则覆盖不全，无法穷举所有反爬场景
- 规则之间可能冲突，难以优化组合策略
- 无法量化效果，不知道策略是否真的有效
- 无法学习进化，反爬系统升级后规则失效
- 无法处理模糊信号（微弱特征组合）

AI 驱动的核心价值：从"如果A则做B"的硬编码规则，进化为"根据当前状态预测最优动作，并根据结果持续优化"的闭环系统。

### 5.2 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    AI 反爬策略引擎                        │
├─────────────┬───────────────┬───────────────────────────┤
│  感知层      │  决策层        │  学习层                    │
│             │               │                           │
│ 信号收集     │ 状态评估       │ 效果反馈                  │
│ 特征提取     │ 策略推荐       │ 模型更新                  │
│ 状态编码     │ 动作选择       │ 规则进化                  │
│             │               │                           │
│ 输出：State  │ 输出：Action  │ 输入：Reward              │
└─────────────┴───────────────┴───────────────────────────┘
         │              │                   │
         ▼              ▼                   ▼
    浏览器状态      执行动作            结果数据
    (50+ 特征)     (10+ 可选动作)      (成功/失败/被检测)
```

### 5.3 感知层设计

#### 5.3.1 特征清单（State Vector）

| 类别 | 特征 | 类型 | 说明 |
|------|------|------|------|
| **指纹特征** | fingerprint_score | float | 当前指纹质量评分 (0-100) |
| | fingerprint_age_hours | float | 指纹使用时长（小时） |
| | fingerprint_uses | int | 指纹累计使用次数 |
| | fingerprint_region_match | bool | 指纹地区与目标网站地区是否匹配 |
| **代理特征** | proxy_latency_ms | int | 代理延迟（毫秒） |
| | proxy_region_match | bool | 代理地区与目标网站地区是否匹配 |
| | proxy_type | enum | 代理类型（residential/datacenter/mobile） |
| | proxy_age_hours | float | 代理使用时长 |
| **页面特征** | page_load_time_ms | int | 最近一次页面加载时间 |
| | page_status_code | int | 最近一次 HTTP 状态码 |
| | page_has_captcha | bool | 页面是否包含验证码元素 |
| | page_has_block_keyword | bool | 页面是否包含拦截关键词 |
| | page_content_hash_match | bool | 页面内容哈希是否与预期一致 |
| **行为特征** | avg_action_interval_ms | int | 最近 10 次操作的平均间隔 |
| | action_interval_std | float | 操作间隔标准差（衡量规律性） |
| | click_position_deviation | float | 点击位置偏离元素中心的平均距离 |
| | recent_success_rate | float | 最近 20 次操作的成功率 |
| | consecutive_failures | int | 连续失败次数 |
| **网络特征** | request_success_rate | float | 最近 50 次请求的成功率 |
| | http_403_count | int | 最近 50 次请求中 403 的数量 |
| | http_429_count | int | 最近 50 次请求中 429 的数量 |
| | avg_request_latency_ms | int | 平均请求延迟 |
| **历史特征** | site_detection_frequency | float | 该网站过去的被检测频率（0-1） |
| | fingerprint_site_success_rate | float | 当前指纹在该网站的历史成功率 |
| | similar_scenario_best_action | enum | 类似历史场景的最优动作 |
| | time_since_last_detection | float | 距离上次被检测的时间（分钟） |

**特征总数**：约 30 个核心特征（经过特征选择后）

#### 5.3.2 特征工程

- **归一化**：所有数值特征归一化到 [0, 1] 或标准化为均值 0 方差 1
- **缺失值处理**：新网站/新指纹没有历史数据时，用全局均值填充，或标记为"未知"
- **特征选择**：用随机森林的 feature_importances_ 或 L1 正则化筛选最有效的 15-20 个特征
- **特征交互**：构造组合特征，如 `fingerprint_region_match AND proxy_region_match`（两者都匹配才是真安全）

### 5.4 决策层设计

#### 5.4.1 动作空间（Action Space）

| 动作 | 类别 | 风险等级 | 说明 |
|------|------|---------|------|
| keep_fingerprint | 指纹 | 低 | 保持当前指纹不变 |
| switch_fingerprint | 指纹 | 中 | 切换到备用指纹 |
| refresh_fingerprint_noise | 指纹 | 低 | 刷新 Canvas/Audio 噪声（不改变其他属性） |
| keep_proxy | 代理 | 低 | 保持当前代理 |
| switch_proxy | 代理 | 中 | 切换代理节点 |
| switch_proxy_region | 代理 | 中 | 切换代理地区 |
| normal_speed | 节奏 | 低 | 正常操作频率 |
| slow_down | 节奏 | 低 | 降低操作频率（增加 2-5 秒延迟） |
| pause_5min | 节奏 | 中 | 暂停操作 5 分钟 |
| enable_safe_click | 行为 | 低 | 启用安全点击（模拟人类鼠标轨迹） |
| enable_human_type | 行为 | 低 | 启用人类化输入（模拟打字节奏） |
| keep_cookies | 清理 | 低 | 保持 Cookie 不变 |
| clear_cookies | 清理 | 高 | 清理当前站点 Cookie（可能导致登出） |
| clear_storage | 清理 | 高 | 清理 localStorage/sessionStorage |

**动作总数**：15 个基础动作，可组合为复合动作（如 switch_fingerprint + slow_down）

#### 5.4.2 决策算法

**第一阶段：上下文老虎机（Contextual Bandit）**

算法：LinUCB（Linear Upper Confidence Bound）

```
输入：当前状态特征向量 x (d 维)
输出：最优动作 a

对于每个动作 a：
    θ_a = 该动作的线性模型参数 (d 维)
    A_a = 该动作的特征协方差矩阵 (d×d)
    b_a = 该动作的奖励加权特征和
    
    预测收益：p_a = θ_a^T · x
    不确定性：u_a = α * sqrt(x^T · A_a^{-1} · x)
    上置信界：UCB_a = p_a + u_a

选择：a = argmax(UCB_a)

执行动作 a 后，观察奖励 r：
    A_a ← A_a + x · x^T
    b_a ← b_a + r · x
    θ_a ← A_a^{-1} · b_a
```

**优点**：
- 实现简单，计算量小（适合移动端）
- 天然处理"探索 vs 利用"平衡（不确定性高的动作有额外加分）
- 可解释性强（每个动作的预测收益和不确定性都可输出）

**第二阶段：强化学习（DQN / Policy Gradient）**

当数据量足够（>10000 条操作记录）后，可升级为深度强化学习：

- **状态**：当前状态 + 最近 N 步历史（序列数据，用 LSTM 编码）
- **动作**：15 个基础动作 + 复合动作
- **奖励**：即时奖励 + 延迟奖励（执行后 5 分钟内的表现）
- **算法**：DQN（离散动作空间）或 PPO（连续参数化动作）

**第三阶段：规则兜底 + AI 优化**

无论 AI 模型多先进，都必须有规则兜底层：

```
AI 推荐动作 a
    │
    ▼
规则校验：
    ├── 是否同时做了 2+ 个高风险动作？──是──▶ 拒绝，选择次优
    ├── 是否在冷却期切换指纹？──────────是──▶ 拒绝
    ├── 是否忽略了高风险信号？──────────是──▶ 强制加入应对动作
    ├── 动作频率是否过高（1分钟内>3次）？─是──▶ 拒绝，建议等待
    └── 是否通过所有校验？──────────────是──▶ 执行
```

### 5.5 学习层设计

#### 5.5.1 奖励函数设计（Reward Function）

| 事件 | 奖励 | 说明 |
|------|------|------|
| 操作成功（页面正常返回，无异常） | +1 | 基础奖励 |
| 连续 10 次操作无异常 | +5 | 稳定奖励（鼓励持续成功） |
| 完成目标任务（成功登录/抓取数据） | +20 | 任务级奖励（最终目标） |
| 出现验证码 | -5 | 轻度惩罚 |
| 返回 403/429 | -10 | 中度惩罚 |
| 检测到拦截页 | -15 | 中重度惩罚 |
| IP 被封禁 | -50 | 重度惩罚（最严重） |
| 策略执行后 5 分钟内无异常 | +10 | 延迟奖励（验证策略真的有效） |
| 策略执行后 30 分钟内复发 | -20 | 延迟惩罚（策略只是暂时有效） |

**关键设计**：
- **延迟奖励**：切换指纹后立即返回 200 不代表成功，可能 2 分钟后才被检测。执行策略后观察 5 分钟，再根据结果给延迟奖励
- **信用分配**：一个成功的结果可能是前面 5 个动作共同导致的。用时间差分（TD）或优势函数（Advantage）将功劳分配给每个动作
- **奖励塑形**：给中间步骤一些引导性奖励（如"切换指纹后页面加载正常"给 +2），最终目标奖励给大奖励（+20），加速学习

#### 5.5.2 在线学习

- **更新频率**：每次操作后立即更新 Bandit 模型参数（增量更新，计算量小）
- **重训练频率**：每 1000 次操作或每 24 小时，用积累的数据全量重训练特征选择和模型参数
- **学习率衰减**：随着数据量增加，逐渐降低学习率，避免新数据过度影响稳定的模型
- **经验回放**：保留最近 10000 条操作记录，训练时随机采样，避免时序相关性

#### 5.5.3 概念漂移检测

**检测指标**：
- 策略成功率滑动窗口（最近 100 次 vs 之前 100 次）
- 被检测频率变化（最近 7 天 vs 之前 7 天）
- 最优动作分布变化（AI 推荐的动作类型是否发生显著变化）

**检测算法**：
- 统计检验：KS 检验（比较两个分布是否相同）、t 检验（比较均值）
- 阈值触发：成功率下降 > 20%，或被检测频率上升 > 50%

**响应策略**：
- 轻度漂移：提高学习率，加速适应
- 中度漂移：触发全量重训练，重置部分模型参数
- 重度漂移：回退到规则引擎，同时收集新数据重新训练

#### 5.5.4 冷启动处理

**问题**：新安装的 App 没有历史数据，AI 模型无法决策。

**解决方案**：
1. **预置通用模型**：在开发阶段用多种场景预训练一个"通用策略模型"，作为初始模型
2. **规则引擎兜底**：数据量 < 100 条时，主要用规则引擎决策，AI 模型只做参考
3. **迁移学习**：从类似网站/类似指纹的经验迁移，用小数据微调
4. **主动探索**：冷启动期增加探索比例（ε-greedy 的 ε 设为 0.3），快速积累数据
5. **数据共享**：用户可选择导入他人的训练数据（脱敏后），加速冷启动

### 5.6 模型可解释性

AI 模型不能是黑盒，每次决策都需要输出"为什么"：

```json
{
  "recommended_action": "switch_fingerprint",
  "confidence": 0.82,
  "reasoning": {
    "key_factors": [
      {"feature": "consecutive_failures", "value": 3, "impact": "high", "contribution": 0.35},
      {"feature": "page_has_captcha", "value": true, "impact": "high", "contribution": 0.28},
      {"feature": "fingerprint_score", "value": 58, "impact": "medium", "contribution": 0.18}
    ],
    "alternative_actions": [
      {"action": "slow_down", "expected_reward": 2.1, "reason": "降低频率可能缓解限流，但不能解决指纹被标记问题"},
```

- **SHAP 值**：计算每个特征对预测结果的贡献度

- **历史对比**：展示类似历史场景的处理方式和效果
- **替代方案对比**：列出其他可选动作的期望收益和原因

- `fingerprint_set`：显示指纹图标 + 切换前后对比（旧指纹→新指纹）
- `antidetect_adjust`：显示盾牌图标 + 调整策略 + 调整结果
- `fingerprint_test`：显示检测图标 + 评分（带颜色：绿>80，黄60-80，红<60）
- 普通 browser 操作：在卡片角落显示当前指纹评分小图标

#### 7.4.3 全局状态指示

在浏览器页面顶部显示一个小型反爬状态指示器：

- 绿色（健康）：当前指纹评分 > 80，无活跃信号
- 黄色（注意）：评分 60-80，或有 low/medium 级别信号
- 红色（警告）：评分 < 60，或有 high/critical 级别信号
- 点击指示器可查看详细状态和快速操作

## 8. 安全与隐私设计

### 8.1 数据安全

| 数据类型 | 存储方式 | 加密 | 说明 |
|---------|---------|------|------|
| 指纹配置 | SQLite (Room) | 否 | 不包含敏感信息，只是浏览器参数 |
| 检测记录 | SQLite (Room) | 否 | 评分和风险项，不包含页面内容 |
| 操作日志 | SQLite (Room) | 否 | 只记录动作类型和参数，不记录页面内容 |
| 策略效果 | SQLite (Room) | 否 | 状态特征向量（已脱敏），不包含原始数据 |
| AI 模型参数 | JSON 文件 | 否 | 模型权重，不包含用户数据 |
| 代理配置 | SQLite (Room) | 是 (AES-256) | 包含代理密码等敏感信息 |
| Cookie | WebView 管理 | 系统级 | 由 WebView 安全沙箱管理 |

### 8.2 隐私保护

1. **本地存储**：所有数据本地存储，不上传云端，不与第三方共享
2. **数据最小化**：只记录元数据（状态码、延迟、动作类型），不记录页面内容、表单输入、个人信息
3. **用户可控**：用户可随时查看、导出、删除所有数据；可关闭 AI 学习功能（停止数据收集）
4. **匿名化**：状态特征向量不包含可识别个人身份的信息（如具体 URL 只保留域名，不保留路径和参数）
5. **使用边界**：
   - 不支持针对特定网站的攻击模式
   - 遵守 robots.txt 协议
   - 设置操作频率上限（防止滥用）
   - 不用于非法用途

### 8.3 注入脚本安全

1. **脚本来源可信**：所有注入脚本由项目维护，代码开源可审计，不包含远程加载
2. **脚本最小权限**：注入脚本只重写必要的 API，不访问页面数据，不发送网络请求
3. **脚本完整性校验**：注入脚本在构建时计算哈希，运行时校验，防止被篡改
4. **CSP 兼容**：注入脚本兼容页面的 Content Security Policy，不触发 CSP 违规

### 8.4 密钥安全

- 代理密码等敏感信息使用 Android Keystore 加密存储
- 加密密钥由系统安全硬件（TEE）保护，不可导出
- 不硬编码任何密钥，所有密钥通过安全配置注入

## 9. 性能设计

### 9.1 性能预算

| 环节 | 预算 | 说明 |
|------|------|------|
| JS 注入脚本体积 | < 20KB（gzip 后 < 8KB） | 合并所有指纹伪装脚本 |
| 注入脚本执行时间 | < 5ms | 页面加载时同步执行，不阻塞渲染 |
| Canvas 噪声处理（1080p） | < 20ms | toDataURL 时的额外延迟 |
| Canvas 噪声处理（4K） | < 100ms | 大画布分块处理 |
| 指纹切换（不重载页面） | < 100ms | 只更新配置，下次页面加载生效 |
| 指纹切换（重载页面） | 页面加载时间 | 与正常页面加载相同 |
| AI 决策推理 | < 10ms | 上下文老虎机，计算量小 |
| AI 模型更新 | < 50ms | 增量更新，操作后异步执行 |
| 反爬信号检测 | < 5ms/操作 | 每次操作后检查，不阻塞 |
| 数据库写入 | < 10ms | 异步写入，不阻塞主线程 |

### 9.2 性能优化策略

1. **脚本合并**：所有指纹注入脚本合并为一个，减少注入次数和解析开销
2. **延迟初始化**：Canvas/Audio 噪声处理只在对应 API 被调用时执行，不预计算
3. **缓存策略**：
   - 同一画布多次 toDataURL 使用相同噪声种子（避免重复计算）
   - AI 预测结果缓存（相同状态不重复推理）
   - 指纹配置缓存（当前配置常驻内存）
4. **异步处理**：
   - 数据库写入异步执行
   - AI 模型更新异步执行
   - 反爬信号检测异步执行
5. **降级策略**：
   - 设备性能低时，自动降低 Canvas 噪声精度（分块更大）
   - 内存不足时，减少操作日志保留时长
   - 可在设置中关闭 AI 学习（减少计算开销）

### 9.3 性能监控

- 记录每次注入脚本执行时间
- 记录每次 Canvas 噪声处理时间
- 记录每次 AI 决策推理时间
- 性能数据写入日志，超过预算时告警
- 设置页面可查看性能统计

### 13.2 常见问题

**Q: 为什么不直接用独立的 Chromium（如 Crosswalk）？**
A: 独立 Chromium 会增加 APK 体积 50-100MB，且维护成本高。当前基于系统 WebView 可以满足大部分需求，未来如需要更完整的指纹控制再考虑。

**Q: 指纹伪装会影响正常网页的使用吗？**
A: 不会。指纹伪装只修改浏览器 API 的返回值，不影响页面渲染和功能。Canvas 噪声人眼不可见，Audio 噪声只影响高频区域。

**Q: AI 模型会收集我的浏览数据吗？**
A: 不会。AI 模型只记录元数据（动作类型、状态码、延迟等），不记录页面内容、表单输入、个人信息。所有数据本地存储，不上传云端。

**Q: 可以关闭指纹伪装吗？**
A: 可以。在设置中可以全局关闭指纹伪装，也可以针对特定网站关闭。关闭后浏览器使用真实指纹。

**Q: 为什么需要 AI 驱动？规则引擎不够吗？**
A: 规则引擎只能处理已知场景，无法处理新型反爬和模糊信号。AI 驱动可以从数据中学习最优策略，持续进化，适应反爬技术的变化。
