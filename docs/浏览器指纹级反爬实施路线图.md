## 第一阶段：基础指纹（1-2天，收益最大）

> 目标：实现最容易获取、修改成本最低、反爬收益最大的基础指纹项伪装。
> 优先级：最高。完成后即可应对 60% 以上的基础反爬检测。

### 任务 1.1：User-Agent 池建设

**目标**：建立一个覆盖主流浏览器/OS/设备的 UA 池，支持随机选择和任务级隔离。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |
|--------|------|---------|---------|------|
| 1.1.1 | 收集主流 UA 列表 | 收集 Chrome(90-120)、Safari(15-17)、Firefox(100-120)、Edge(90-120)，覆盖 Windows/macOS/Linux/Android/iOS，每个版本至少 2 个变体 | 至少 50 条真实 UA，按浏览器/版本/OS 分类 | 列表文件存在，分类清晰，无重复 | 0.5天 |
| 1.1.2 | 设计 UA 池数据结构 | 字段：uaString、browserType、browserVersion、osType、osVersion、deviceType、marketShare、releaseDate | 支持按条件筛选（如"Chrome + Windows + 桌面"） | 数据类定义完整，序列化正常 | 0.5天 |
| 1.1.3 | 实现 UA 池管理类 | 功能：加载池、随机选择、按条件筛选、按市场份额加权随机、获取与指定 OS 匹配的 UA | 单例模式，线程安全，支持热更新 | 单元测试覆盖随机选择和筛选逻辑 | 0.5天 |
| 1.1.4 | 集成到 WebView 设置 | 在 BrowserController 中调用 WebSettings.setUserAgentString()，页面加载前生效 | 与 WebView 生命周期绑定，切换标签页时保持一致 | 手动验证 navigator.userAgent 返回设置值 | 0.5天 |
| 1.1.5 | 任务级 UA 隔离 | 不同 AI 任务自动分配不同 UA，同一会话内多任务互不影响；任务结束后 UA 回收 | 任务开始时分配，任务结束时标记可用，避免 UA 复用被关联 | 连续 5 个任务使用不同 UA | 0.5天 |

### 任务 1.2：WebRTC 防护

**目标**：阻止 WebRTC 泄露真实 IP 地址（内网/公网），这是最常见的 IP 泄露途径。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |
|--------|------|---------|---------|------|
| 1.2.1 | 研究 WebRTC 指纹原理 | 分析 RTCPeerConnection、ICE candidate 收集流程、STUN/TURN 服务器交互 | 理解 IP 泄露的完整链路 | 输出技术分析笔记 | 0.5天 |
| 1.2.2 | 编写 WebRTC 防护注入脚本 | 重写 RTCPeerConnection 构造函数、阻止 createDataChannel、拦截 onicecandidate、返回空 candidate 列表 | 脚本体积 < 2KB，不影响正常页面功能 | 脚本通过语法检查，无运行时错误 | 0.5天 |
| 1.2.3 | 实现注入时机控制 | 在页面任何脚本执行前注入（通过 shouldInterceptRequest 拦截 HTML，在 <head> 首行注入） | 注入时机早于页面所有 JS 执行 | 用测试页面验证注入先于页面脚本 | 0.5天 |
| 1.2.4 | 验证防护效果 | 用 browserleaks.com/webrtc、ipleak.net 等网站测试，确认不泄露真实 IP | 测试页面显示"WebRTC disabled"或无 ICE candidate | 至少 3 个测试网站通过 | 0.5天 |

### 任务 1.3：基础属性伪装

**目标**：伪装 navigator 和 screen 对象下的基础硬件/系统属性，使其与 UA 声明的环境一致。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |
|--------|------|---------|---------|------|
| 1.3.1 | navigator.hardwareConcurrency 伪装 | 重写属性返回值，范围 4-16，与 UA 声明的设备档次匹配（高端机 8+，低端机 4-6） | 使用 Object.defineProperty，不可枚举，不可重新配置 | 手动验证返回值在设定范围内 | 0.25天 |
| 1.3.2 | navigator.deviceMemory 伪装 | 重写属性返回值，范围 4-16GB，与 hardwareConcurrency 正相关 | 与 CPU 核心数保持合理比例（每核 1-2GB） | 两者比例合理 | 0.25天 |
| 1.3.3 | navigator.plugins 伪装 | 标准化插件列表（Chrome PDF Viewer、Chromium PDF Viewer 等），隐藏系统特有插件 | 返回固定的 3-5 个常见插件，长度和名称与 UA 匹配 | 不同设备返回相同的插件列表 | 0.25天 |
| 1.3.4 | navigator.platform 伪装 | 与 UA 匹配（Win32→Windows，MacIntel→macOS，Linux x86_64→Linux，iPhone→iOS） | 从 UA 解析自动推导，确保一致 | platform 与 UA 声明的 OS 一致 | 0.25天 |
| 1.3.5 | screen 属性伪装 | 色深固定 24，像素比范围 1-3，与设备类型匹配（移动端 2-3，桌面端 1-2） | 不修改物理分辨率（无法修改），只修改可修改的属性 | colorDepth=24，pixelRatio 合理 | 0.25天 |

### 任务 1.4：一致性校验引擎

**目标**：确保所有伪装的指纹项内部一致，不一致时自动修正或告警。这是指纹伪装的生命线——不一致反而成为更强特征。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |
|--------|------|---------|---------|------|
| 1.4.1 | 设计一致性规则库 | 规则示例：UA(Chrome+Win)→platform=Win32；UA(macOS)→language可能含en；时区(美国)→language不应是zh-CN；WebGL(高端显卡)→hardwareConcurrency≥8 | 至少 20 条规则，覆盖常见组合 | 规则文档完整，每条有正反例 | 0.5天 |
| 1.4.2 | 实现校验函数 | 输入：指纹配置对象；输出：不一致项列表 + 修正建议 | 校验速度 < 10ms，支持增量校验 | 单元测试覆盖 10+ 不一致场景 | 0.5天 |
| 1.4.3 | 自动修正机制 | 检测到不一致时，以 UA 为基准自动修正其他属性（如 platform、语言默认值） | 修正后再次校验通过，修正日志可追溯 | 自动修正后一致性校验通过 | 0.5天 |
| 1.4.4 | 运行时监控 | 在浏览器操作过程中，定期检查指纹是否被页面脚本恢复（页面可能重置被修改的属性） | 检测到被恢复时重新注入，记录告警 | 页面尝试重置时能检测并恢复 | 0.5天 |

## 第二阶段：核心指纹（3-5天）

> 目标：实现 Canvas、WebGL、字体这三个最核心、最常用的渲染指纹的随机化/伪装。
> 优先级：高。完成后可应对 85% 以上的常规反爬检测。

### 任务 2.1：Canvas 指纹随机化

**目标**：通过在 Canvas 像素数据中添加符合统计分布的微小噪声，使每次 Canvas 指纹哈希值不同，但人眼不可见。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |
|--------|------|---------|---------|------|
| 2.1.1 | 研究 Canvas 指纹检测原理 | 分析 toDataURL、getImageData、isPointInPath、measureText 等 API 在指纹检测中的用法；理解文字渲染、渐变、阴影的差异来源 | 输出技术分析文档，列出所有可被利用的 API | 文档完整，覆盖至少 5 个 API | 0.5天 |
| 2.1.2 | 设计噪声算法 | 像素级噪声：RGB 各通道 ±1-2 的随机扰动；噪声符合高斯分布而非均匀分布；只影响低字节（人眼不可见）；大画布时分块处理避免性能问题 | 噪声不可见（PSNR > 40dB），哈希变化率 > 99% | 用 10 张测试图验证不可见性和哈希变化 | 1天 |
| 2.1.3 | 编写 Canvas 注入脚本 | 重写 HTMLCanvasElement.prototype.toDataURL、toBlob、getContext；重写 CanvasRenderingContext2D.prototype.getImageData、isPointInPath；确保所有获取像素的途径都被噪声处理 | 脚本体积 < 5KB，兼容 Canvas 2D 和 WebGL canvas | 单元测试覆盖所有被重写的 API | 1天 |
| 2.1.4 | 性能优化 | 大画布（>4K）时降采样处理；缓存噪声模式（同一画布多次 toDataURL 使用相同噪声，避免闪烁）；Web Worker 处理大画布 | 1080p 画布 toDataURL 延迟增加 < 20ms；4K 画布 < 100ms | 性能基准测试达标 | 0.5天 |
| 2.1.5 | 验证效果 | 用 browserleaks.com/canvas、amiunique.org、creepjs 测试；确认 Canvas 指纹哈希每次变化；确认视觉无差异 | 至少 3 个测试网站显示 Canvas 指纹变化；截图对比无可见差异 | 全部测试通过 | 0.5天 |

| 2.2.2 | 收集主流显卡信息库 | 收集 NVIDIA（RTX 30/40 系列、GTX 16 系列）、AMD（RX 6000/7000 系列）、Intel（UHD/Iris Xe）、Apple（M1/M2/M3）的显卡信息；每个型号包含 vendor、renderer、市场份额 | 至少 30 个显卡型号，按品牌/档次分类 | 信息库文件完整，无重复 | 0.5天 |
| 2.2.3 | 编写 WebGL 注入脚本 | 重写 WebGLRenderingContext.prototype.getParameter（拦截 37445/37446 常量）、getSupportedExtensions（标准化扩展列表）；同时处理 WebGL2RenderingContext | 与 Canvas 脚本合并注入，体积 < 3KB | 手动验证 getParameter 返回伪装值 | 0.5天 |
| 2.2.4 | 与 UA/硬件配置一致性匹配 | 高端显卡（RTX 4090）→ hardwareConcurrency≥16、deviceMemory≥16GB；集成显卡（UHD）→ 4-8 核、4-8GB；Apple Silicon → platform=MacIntel | 从指纹配置文件统一生成，确保一致 | 一致性校验通过 | 0.5天 |

### 任务 2.4：注入时机优化

**目标**：确保所有指纹伪装脚本在页面任何 JS 执行之前注入，这是指纹伪装有效的前提。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |

## 第三阶段：高级指纹（5-7天）

> 目标：实现 Audio 指纹、反检测加固、指纹配置文件管理、指纹质量自检。
> 优先级：中高。完成后可应对 95% 以上的专业反爬检测。

### 任务 3.1：Audio 指纹伪装

**目标**：在 Web Audio API 的频域数据中添加微小噪声，使 Audio 指纹每次不同。这是最容易被忽略但非常稳定的指纹。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |
|--------|------|---------|---------|------|
| 3.1.1 | 研究 Audio 指纹检测原理 | 分析 AudioContext、OscillatorNode、DynamicsCompressorNode、AnalyserNode 的组合用法；理解音频处理管线差异来源 | 输出技术分析文档 | 文档完整，包含信号流图 | 0.5天 |
| 3.1.2 | 设计音频噪声算法 | 在 AnalyserNode 的 getByteFrequencyData/getFloatFrequencyData 返回值中添加 ±1-2 的微小扰动；噪声符合音频信号的统计特性；只影响高频部分（人耳不敏感） | 噪声不影响正常音频播放质量 | 用测试音频验证音质无差异 | 1天 |
| 3.1.3 | 编写 Audio 注入脚本 | 重写 AudioContext.prototype.createAnalyser；重写 AnalyserNode.prototype.getByteFrequencyData、getFloatFrequencyData、getByteTimeDomainData；重写 OfflineAudioContext | 脚本体积 < 3KB，不影响音频播放 | 单元测试覆盖所有被重写的 API | 1天 |
| 3.1.4 | 性能优化 | 避免在音频播放时引入延迟；大数组处理时使用类型化数组；缓存噪声模式 | 音频播放无卡顿、无爆音 | 连续播放 10 分钟音频无异常 | 0.5天 |
| 3.1.5 | 验证效果 | 用 browserleaks.com/audio、audiofingerprint.openwpm.com 测试，确认 Audio 指纹哈希变化 | 至少 2 个测试网站显示指纹变化 | 全部测试通过 | 0.5天 |

### 任务 3.2：反检测加固

**目标**：防止反爬系统检测到我们的指纹伪装（被检测到伪装本身就是最强的特征）。这是指纹伪装的最高境界。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |
|--------|------|---------|---------|------|
| 3.2.1 | 研究反检测技术 | 分析 toString 检测（被重写的方法 toString 不含 [native code]）、属性描述符检测（Object.getOwnPropertyDescriptor）、Proxy 检测、原型链检测 | 输出反检测技术综述 | 文档覆盖至少 5 种检测方法 | 1天 |
| 3.2.2 | toString 欺骗 | 为所有被重写的原生方法重写 toString，返回 "function xxx() { [native code] }"；同时重写 toString.toString 防止递归检测 | 所有被重写方法的 toString 检测通过 | 用 toString 检测脚本验证 | 0.5天 |
| 3.2.3 | Object.defineProperty 加固 | 使用 Object.defineProperty 替代直接赋值；设置 configurable:false、enumerable:false；重写 getOwnPropertyDescriptor 返回原生描述符 | 属性描述符检测无法识别被修改 | 用描述符检测脚本验证 | 0.5天 |
| 3.2.4 | 隐藏注入脚本特征 | 注入脚本不创建全局变量；不修改 document.currentScript；不留下 DOM 痕迹；使用 IIFE 封装 | 页面无法通过 DOM 扫描发现注入脚本 | 用脚本扫描验证无全局变量泄露 | 0.5天 |
| 3.2.5 | 专业检测工具验证 | 用 CreepJS（最严格的指纹检测工具）、FingerprintJS Pro、amiunique 连续测试 10 次，确认不被检测为自动化/伪装浏览器 | CreepJS 评分 > 70 分（满分 100），不触发自动化告警 | 所有检测工具通过 | 1天 |

### 任务 3.3：指纹配置文件管理

## 第五阶段：模型↔浏览器交互接口（3-5天）

> 目标：将浏览器侧的指纹能力通过完整的工具接口暴露给模型，让模型能**感知、配置、检测、调整**指纹，而不是被动使用固定配置。这是指纹能力从"哑巴功能"变成"智能工具"的关键。
> 优先级：高。没有这一阶段，前四阶段的能力模型都不知道、也不会用。
> 设计原则：每个工具动作都有明确的**使用场景引导**、**参数说明**、**返回结构**、**错误码**，模型通过 description 就能理解什么时候该调用。

### 任务 5.5：工具 description 与智能引导更新

**目标**：更新 BrowserAgentTool 的 description，让模型理解所有指纹相关动作的**使用场景、调用时机、决策逻辑**。这是模型能不能"聪明地"使用指纹能力的关键。

| 子任务 | 内容 | 技术要点 | 验收标准 | 预估 |
|--------|------|---------|---------|------|
| 5.5.1 | 新增指纹动作说明 | 在 description 中添加所有 fingerprint_* 和 antidetect_* 动作的说明，每个动作包含：功能、使用场景、参数、返回、注意事项 | 描述简洁明了，模型能理解每个动作的用途 | 模型测试：给场景，模型能选择正确动作 | 1天 |
| 5.5.2 | 设计指纹使用场景引导 | 编写场景化引导：①访问新网站前→先 fingerprint_get 确认当前指纹合适；②访问国外网站→确保指纹地区与代理地区一致；③连续操作 10 分钟以上→考虑 fingerprint_test 检测是否被标记；④遇到验证码→先 antidetect_signals 分析，再 antidetect_adjust | 引导覆盖至少 10 种常见场景，每种有明确的操作流程 | 模型测试：给定场景，模型能按引导执行 | 0.5天 |
| 5.5.3 | 设计反爬响应决策树 | 编写决策树：①出现图形验证码→fingerprint_test→评分<60→fingerprint_set切换+antidetect_pause冷却；②返回403→browser_network分析→antidetect_adjust(auto)；③Cloudflare拦截页→fingerprint_set切换+等待60s+safe_click；④页面空白→先 view 确认状态→再 navigate 重试；⑤连续3次失败→antidetect_pause+向用户报告 | 决策树覆盖至少 8 种反爬场景，每种有明确的步骤和分支 | 模型测试：模拟反爬场景，模型能按决策树正确响应 | 0.5天 |
| 5.5.4 | 错误码扩展与说明 | 新增指纹相关错误码：FINGERPRINT_MISMATCH（指纹与目标地区不匹配）、ANTIDETECT_TRIGGERED（已被反爬检测，操作被拒绝）、PROXY_FINGERPRINT_MISMATCH（代理地区与指纹地区不一致）、FINGERPRINT_COOLING（指纹冷却中，不可用）、FINGERPRINT_QUALITY_LOW（指纹质量评分过低，建议切换）；每个错误码有明确的含义和建议操作 | 错误码在 envelope 的 error_code 字段返回，模型可根据错误码决策 | 单元测试覆盖所有新错误码 | 0.5天 |
| 5.5.5 | 禁忌清单更新 | 在 description 的禁忌清单中添加：①不要在同一指纹下频繁切换 IP（容易被关联）；②不要在被检测后继续同样的操作（应先切换指纹）；③不要忽略 antidetect_signals 的高风险信号；④不要在 fingerprint_test 评分 < 50 时继续操作；⑤不要同时切换指纹+代理+Cookie（变化太大会被怀疑） | 禁忌清单至少 10 条，每条有原因说明 | 模型测试：模型不会违反禁忌清单 | 0.25天 |
