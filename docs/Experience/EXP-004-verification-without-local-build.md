## 1. 问题现象

沙箱环境**无 Android SDK**：`./gradlew` 任何编译任务都跑不了。如果因此跳过验证直接推送，就是把回归测试完全交给运气。

## 2. 根因分析

验证责任不能消失，只能重新分层。本地缺的不是"验证"，是"全量验证的手段"；仍保留**静态验证**与**分块编译**能力，把**全量编译/单测/lint/detekt** 移交云端 CI 门禁，产物验收在下载受阻时改用配置与元数据互证。

## 3. 解决方案

### 3.1 第一层：本地静态验证（无论有没有 SDK 都能做）

- 逐文件 diff 自查，重点查类型推断、空安全、返回值引用（本次 `.key` 回归若在此层可挡住，见 3.3）。
- 补丁文件对原始快照 `patch --dry-run`，确认可干净应用、无 hunk 冲突。
- 脚本类改动（`.sh` / python）本地可执行 `sh -n` / `python3 -m py_compile`——这正是 `ci.yml` 第一道步骤同款检查。

### 3.2 第二层：本地分块编译（有 SDK 时）→ 云端全量门禁（本项目沙箱常态）

按 [AGENTS.md 变更面 → 编译块路由表](../../AGENTS.md#1-变更面--编译块路由表提交前必过对应块)在本地跑对应编译块；**无 SDK 时分块编译整体移交云端**：每次 push 后盯 `ci.yml`（skill 脚本语法检查 → release 全量编译 → `:app:testReleaseUnitTest` → lint → detekt），红即修，修完重推，**不许无验证推送编译型改动**。

### 3.3 第三层：把云端门禁当第一道回归网（真实战果）

v0.0.1.10 期间两次回归全靠它捕获，均未流出问题安装包：

| 回归 | 门禁捕获点 | 本地本可怎么挡 |
|---|---|---|
| `sessions.remove(oldest)` 漏 `.key` → 类型推断失败 | Kotlin 编译步骤 | 有 SDK 时 `:app:compileDebugKotlin` 秒挡；无 SDK 时靠 3.1 静态自查 |
| init 块签名变化致 detekt baseline 失配 | detekt 步骤 | 见 [EXP-002](./EXP-002-detekt-baseline-signature-mismatch.md) |

**结论：云端门禁不是"最后一道"，是这套体系里第一道会跑代码的网。盯门禁结果是推送动作的一部分，不是可选项。**

### 3.4 产物验收：下载被阻断时的三角验证

Release APK 下载被网络阻断时（见 [EXP-001](./EXP-001-github-rest-api-push-channel.md)），不死磕传输，用三侧互证：

1. **构建配置侧**：`app/build.gradle.kts` 的 `abiFilters`（仅 arm64-v8a → 必含 `lib/arm64-v8a/*.so`）、`sourceSets` 资产目录（`src/_armAssets` → `assets/container/` 双架构 rootfs）、`packaging` 规则。
2. **工作流侧**：`android-release.yml` 的构建任务（`:app:assembleRelease`）与产物重命名规则，与实际资产名逐字对照。
3. **元数据侧**：资产大小（37,720,353 字节）与"30MB+ Alpine rootfs + native 库"的量级对照。

三侧互证即采信；任何一侧对不上才需要深查。

## 4. 验证方法

- 门禁盯梢：`GET /repos/{owner}/{repo}/actions/runs/{run_id}` 轮询 `conclusion == "success"`；或 `GET .../commits/{sha}/check-runs`。
- 三角验证输出一张三列对照表（配置声明 / 工作流行为 / 实际元数据），全部打勾才算验收通过。
