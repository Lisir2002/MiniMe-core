# 实战经验库（docs/Experience/）

> **目的：让每个坑只被踩一次。** 这里沉淀本项目（含 AI 协同开发、沙箱环境、云端 CI）实战中真实遇到的问题、根因与解法。不是理论资料库——每条经验都来自我们的实际战场，并随环境变化持续更新。

## 体系规则

### 1. 什么时候必须写经验文档

| 触发条件 | 说明 |
|---|---|
| CI 门禁失败（任意一次，含编译/单测/lint/detekt/发版链路） | 修完必须沉淀，写清门禁为什么没在本地挡住 |
| 工具链 / 网络 / 环境问题导致工作受阻 | 如沙箱网络阻断、脚本解释器差异、API 行为与文档不符 |
| 同一问题第二次出现 | 说明第一次没沉淀到位，须回看并补全原经验文档 |
| 采用了非惯例的解法或手法 | 下次换人或换会话，按文档即可复现，不靠口头传承 |
| 规则文档（AGENTS.md / 工作流程规范）发生变更 | 变更依据若是实战教训，必须同步落一篇经验文档，规则与经验双向引用 |

### 2. 命名与编号

- 文件名：`EXP-NNN-<英文短名>.md`，NNN 三位序号只增不复用；英文短名 3-6 个单词概括主题。
- 一篇文档只讲一个主题；同一主题的新发现写进同一篇的「更新记录」，不新开文件。
- 序号与索引登记在本文档「经验索引」表，新增时必须同步登记。

### 3. 文档结构（模板见 `_template.md`）

每篇必须包含：**元数据表**（状态/严重度/分类/创建/最后验证/关联）、**问题现象**（写清"什么场景下会踩到"，方便检索）、**根因**（追到系统层，不停留在报错行）、**解决方案**（分步、命令可复制）、**验证方法**、**预防与规则沉淀**（改动了哪条规则/以后怎么自动挡）、**更新记录**（追加式表格）。

### 4. 更新协议（活文档，硬性要求）

经验文档不是写完就封存，**必须根据我们的实际情况持续更新**：

- **最后验证日期的语义**：是"有人最后一次确认内容仍然成立"的日期，不是最后编辑日期。编辑了但未重新验证，不许改这个日期。
- **任何人在复用时发现环境变化**（网络策略、工具版本、CI 配置变了导致文档步骤失效）：立即更新正文，并在「更新记录」追加一行（日期 | 改了什么 | 触发事件）。
- **每次相关事件复现**（同样的 CI 失败、同样的报错）：回看对应经验文档，确认步骤仍有效；失效就先修文档再修问题。
- **文档体检**：每个大版本或每季度过一次「经验索引」，把超过 6 个月未验证的条目标为「待验证」，确认过时的标「已归档」并注明归档原因。已归档文档不删除，保留检索价值。
- **关联规则双向同步**：经验中固化的规则要进 AGENTS.md / 工作流程规范；规则引用的实战依据指向对应 EXP 文档。

### 5. 防腐烂机制（体系设计依据）

本体系按业界验证过的做法设计，核心是给文档装上"腐烂信号"：

- **文档即代码**：经验文档与代码同仓（`docs/Experience/`），随代码一起版本管理、一起 review；不放进没人看的 wiki。
- **具名 + 日期 + 触发器**：每篇文档有元数据表（创建人、最后验证日期、关联事件），替代"团队共有=没人负责"。
- **症状命名而非系统命名**：标题写"踩到的现象"（如"资产下载连接被重置"），不写系统名——三个月后搜的是症状。
- **缓解优先 + 精确命令**：解决方案先给能立刻止血的步骤，命令必须精确到可复制，禁止"检查一下日志"这种步骤。
- **无指责**：根因写系统与流程为什么允许这个问题发生，不写"谁粗心"。
- **小文档 + 可检索**：一篇一个主题，字段固定，方便按分类/严重度/症状检索。
