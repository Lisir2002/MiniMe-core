# EXP-003：Dependabot PR 一天全红的甄别——时间线对照三分类法

> 一句话：同一天 7 个 Dependabot PR 全部 CI 红，不能一刀切说"依赖更新挂了"；用 check-run 时间线对照自己的推送时间，分三类处置。

| 元数据 | 值 |
|---|---|
| 状态 | 活跃 |
| 严重度 | 主要 |
| 分类 | CI / 依赖管理 |
| 创建日期 | 2026-10-20 |
| 最后验证 | 2026-10-20（5 个 PR rebase 后全部转绿；2 个真实不兼容确认需维护者决策） |
| 创建人 | AI 协同会话（维护者确认） |
| 关联 | PR #5 / #6 / #7 / #9 / #10 / #11 / #13；我的推送 04:40 UTC |

## 1. 问题现象

安全修复推送当天，仓库 7 个 Dependabot PR 的 CI 全部报红。若不甄别直接处理，要么误 rebase 掩盖真实不兼容，要么把"我引入的回归"当成"依赖的锅"。

## 2. 根因分析

全红是三种完全不同的原因叠在一起：

| 分类 | 判定方法 | 本例 |
|---|---|---|
| **我的下游** | PR 的失败 run 时间 == 我推送后的时间；失败点在本次改动的文件 | #10（gradle-wrapper 8.14→9.8.1）04:42 的 run 基线含我引入的 `.key` 编译回归——**先修我自己的，PR 自愈** |
| **旧基线残留** | 失败 run 是 10-14~10-19 在旧 base 上跑的；失败点与 PR 内容无关（如 Kotlin 编译） | #5 / #6 / #7 / #11——rebase 到最新 base 后问题消失 |
| **真实不兼容** | rebase 后仍然红；失败点直指版本要求冲突 | #9：compose BOM 2026.09.00 的 material-ripple 1.12.1 要求 compileSdk 37，项目为 36；#13：依赖组内 Kotlin 2.5.0 要求 Gradle 8.14.4，wrapper 为 8.14 |

**根因认知：Dependabot PR 的红色是"时间快照"，run 的时间戳和基线内容比红色本身更能说明问题。**

## 3. 解决方案

```bash
# ① 看每个 PR 的最新 check-run 时间与结论
GET /repos/{owner}/{repo}/commits/{PR Head sha}/check-runs
#    对比每个 run 的 started_at 与自己推 main 的时间戳 → 三分类
# ② 对"我的下游"和"旧基线残留"类：rebase 复活
POST /repos/{owner}/{repo}/issues/{PR 号}/comments
     {"body": "@dependabot rebase"}
# ③ 对"真实不兼容"类：不 rebase，记录冲突双方版本要求，留维护者决策
#    （升 compileSdk 需连带 AGP 评估；升 Gradle wrapper 影响全量构建链路，都不是 PR 内能解决的）
```

## 4. 验证方法

- rebase 后轮询 `GET /repos/{owner}/{repo}/commits/{新 Head sha}/check-runs`，确认全部 `success`。
- 注意甄别 PR 页面里的**历史 failure 记录**：旧 run 的红色会留在列表里，不代表当前状态；以最新一次 run 为准。

## 5. 预防与规则沉淀

- 推 main 当天顺手看一眼 Dependabot 面板，用时间线区分上下游，别让"我造成的红"归因给依赖更新。
- 真实不兼容项（#9 / #13）记入待办清单，写明冲突双方与所需配套升级，**不默默挂着**——下个发版周期排查依赖问题时容易忘。
- 本方法已纳入 [工作流程规范 章节 2 CI 失败根因分析](../workflow/工作流程规范.md#23-ci-失败要做根因分析)。
