# Version Log

本目录存放 MiniMe-core 项目的所有版本日志，采用统一格式规范。

## 目录结构

```
Version Log/
├── CHANGELOG.md                    # 总版本日志（所有版本汇总，倒序排列）
├── MiniMe-core v-Logs/             # 主应用各版本独立日志
│   ├── MiniMe-core 0.0.0.01 Version Log.md
│   ├── MiniMe-core 0.0.0.02 Version Log.md
│   └── ...
└── MiniMe-Logs v-Logs/             # 附属应用（日志查看器）各版本独立日志
    ├── MiniMe-Logs 0.0.01 Version Log.md
    ├── MiniMe-Logs 0.0.02 Version Log.md
    └── ...
```

## 命名规范

### 文件名版本号（补零格式，仅用于文件命名）

- 文档命名：`{软件名} {补零版本号} Version Log.md`
- 补零规则：每段至少两位，不足补零
  - 主应用四段：`0.0.0.01`、`0.0.0.10`、`0.0.0.17`
  - 附属应用三段：`0.0.01`、`0.0.07`
- 示例：`MiniMe-core 0.0.0.17 Version Log.md`、`MiniMe-Logs 0.0.07 Version Log.md`
- 补零格式仅用于文件命名，方便文件管理器按名称正确排序

### 软件版本号（原格式，用于文档内容与实际发版）

- 文档内容中的版本号、Tag、APK 命名均使用原格式，不补零
- 主应用：`0.0.0.1`、`0.0.0.17`
- 附属应用：`0.0.1`、`0.0.7`
- Tag 命名：主应用 `v{版本号}`（如 `v0.0.0.17`），附属应用 `logviewer-v{版本号}`（如 `logviewer-v0.0.7`）

## 文档格式规范

每个版本日志文档必须严格遵循以下格式：

```markdown
# {软件名} {原格式版本号} Version Log

> {版本简介，100字以内，说明本次更新的核心价值}

**发布日期**：YYYY-MM-DD

### 新功能

- **4-9字小标题**：20-40字简练说明，描述用户可感知的新增功能

### 改进

- **4-9字小标题**：20-40字简练说明，描述体验优化、性能提升、样式调整、逻辑增强等

### 移除

- **4-9字小标题**：20-40字简练说明，描述被删除、弃用或不再支持的功能与组件

### 修复

- **4-9字小标题**：20-40字简练说明，描述修复的问题及症状

### 安全

- **4-9字小标题**：20-40字简练说明，描述安全相关改进

### 已知问题

- **4-9字小标题**：20-40字简练说明，列出当前版本已知但未修复的问题；无则写"无"
```

### 分类说明

| 分类 | 适用场景 | 示例 |
|------|----------|------|
| 新功能 | 用户可感知的新增能力 | 新增模型能力标签、新增预设方案 |
| 改进 | 现有功能的优化与增强 | 性能提升、样式调整、交互优化 |
| 移除 | 功能、组件、配置的删除或弃用 | 移除旧版组件、删除废弃设置项 |
| 修复 | Bug 修复与问题解决 | 修复崩溃、修复显示异常 |
| 安全 | 安全加固与漏洞修复 | 加密增强、权限收紧 |
| 已知问题 | 当前版本存在但未修复的问题 | 特定机型兼容性问题 |

### 格式约束

1. **主标题**：第一行，`# {软件名} {原格式版本号} Version Log`（版本号不补零）
2. **版本简介**：第二行，引用块格式（`>`），100字以内，利益优先、平实语言
3. **发布日期**：ISO 8601 格式（`YYYY-MM-DD`）
4. **分类顺序**：新功能 → 改进 → 移除 → 修复 → 安全 → 已知问题，无内容的分类省略
5. **条目格式**：每条必须为「**4-9字小标题**：20-40字说明」结构，小标题加粗，后接全角冒号，说明句简练明确，描述变化之处而非代码实现
6. **禁止 emoji**：分类标题和正文保持纯文字，简洁专业
7. **破坏性变更**：用「注意」显著标注并说明用户需要做什么
8. **移除条目**：明确说明移除了什么、替代方案是什么（如有）
9. **仅记录应用程序变更（绝对禁止项）**：版本日志只记录用户可感知的应用程序功能、体验、性能、安全变更。绝对禁止出现以下内容：
   - 纯文档变更（README、AGENTS.md、规范文档、发版说明本身的更新）
   - 纯项目配置变更（CI 工作流调整、构建脚本修改、lint 配置，除非直接影响用户体验）
   - 项目管理变更（目录结构调整、文件重命名、仓库维护操作）
   - 纯代码重构（无用户可感知变化的内部重构）
   - 依赖版本升级（除非修复了用户可感知的问题或新增了能力）
   - 发版流程、规范约束、格式调整等元变更
   - 以上变更若确需记录，仅在「改进」分类中以用户可感知的结果描述，不得提及内部实现。
10. **内部重构笼统描述（强制约束）**：品牌名遗留清理、代码架构重构、内部模块合并等用户不可见的技术变更，若发版周期内确需记录，必须使用笼统描述，不得出现具体类名、文件名、函数名、技术术语。标准表述模板：
    - **架构细节优化**：应用架构细节优化，提高产品质量，优化用户体验。
    - **代码质量提升**：内部代码质量持续提升，增强稳定性与可维护性。
    - **项目结构优化**：项目结构优化整理，提升长期可维护性。
    - 禁止表述示例：「删除 BrandMigration.kt」「移除 LegacyPackageDetector」「AIEditorApp 重命名为 MiniMeCore」等涉及内部实现细节的描述。
    - 若内部重构同时带来用户可感知的变化（如性能提升、界面更流畅），应以用户可感知的结果单独成条，不与技术细节混写。
11. **用户可感知边界判定（强制约束）**：版本日志只记录用户可直接感知的结果，不记录实现手段。判定标准与处理规则如下：

    | 内容类型 | 用户可感知？ | 处理方式 |
    |----------|-------------|----------|
    | CI门禁、静态检查、lint规则、代码扫描 | 否 | 禁止写入，或仅以"稳定性提升"笼统描述结果 |
    | 单元测试覆盖率提升、测试用例新增 | 否 | 禁止写入 |
    | 构建速度提升、编译优化、CI流程优化 | 否（仅开发者感知） | 禁止写入 |
    | 代码重构、架构优化、模块合并 | 否 | 按第10条笼统描述 |
    | 崩溃率降低、ANR减少、闪退修复 | 是（间接感知） | 可写"稳定性提升"或具体修复症状 |
    | 启动速度变快、操作更流畅、响应更迅速 | 是（直接感知） | 可写具体体验改善 |
    | 耗电降低、内存占用减少、发热改善 | 是（间接感知） | 可写具体体验改善 |
    | 安全加固、漏洞修复、隐私保护增强 | 是（间接感知） | 可写安全相关改进，不写技术细节 |

    **手段与结果分离原则**：若一条变更同时包含技术手段和用户结果，只保留结果部分，删除手段描述。
    - 反例：「持久化预防：新增数据持久化静态检查与CI门禁，预防设置项重启丢失问题」（混入了"静态检查""CI门禁"等手段）
    - 正例：「持久化加固：多项设置项持久化机制加固，降低重启后配置丢失风险」（仅描述结果）
    - 若手段本身无直接用户可感知结果，则整条删除，不写入版本日志。

## 适用范围

本格式规范适用于项目中所有版本说明文档，包括：
- `docs/Version Log/CHANGELOG.md`（总版本日志）
- `docs/Version Log/MiniMe-core v-Logs/` 下各版本独立文档
- `docs/Version Log/MiniMe-Logs v-Logs/` 下各版本独立文档
- GitHub Release 页面正文说明

所有版本说明必须保持格式一致，不得出现一种文档一个格式的情况。

## 发版流程

1. 代码变更完成并通过编译验证
2. 更新 `CHANGELOG.md`，在 `[Unreleased]` 下方添加新版本条目（遵循条目格式规范）
3. 在对应软件的 `v-Logs/` 目录下创建独立版本日志文档（文件名用补零版本号，内容与 CHANGELOG 一致）
4. commit 并 push 到 main
5. 打 tag 触发云端 CI 构建
6. CI 构建成功后，更新 GitHub Release 标题和说明（Release 正文必须遵循同样的条目格式规范，与版本日志内容一致）
