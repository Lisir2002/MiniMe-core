# 工作流程规范

> 本文档是项目所有工作的"操作手册"：写代码、做设计、修 Bug、管补丁、写注释、发版本、写更新日志、汇报工作，都按这里的步骤走。
> 核心原则：**每一步都要有明确的产出和验收标准，不能"感觉差不多了"就往下走。**
> 面向维护者本人阅读，尽量用大白话，少用黑话。

## 章节 1：编程验证流程

写完代码不是终点，"四层验证全过、达到预期"才是。

### 1.1 四层验证（从快到慢，逐层做）

| 层 | 做什么 | 通过标准 |
| --- | --- | --- |
| 第一层：编译 | 改了 `.kt` / `.gradle.kts` / 清单文件后跑一次编译 | 0 个 error，没有红色报错 |
| 第二层：测试 | 自动测试跑一遍 | 全部测试用例绿，不允许跳过或标"以后再说" |
| 第三层：功能实测 | 手动把改的功能点一遍 | 预期行为全部发生，没新问题 |
| 第四层：关联回归 | 改了 A，顺手测相关的 B、C | 相邻老功能没被改坏 |

常用命令：
- 编译冒烟：`./gradlew :app:assembleDebug`（快，不跑混淆）
- 单元测试：`./gradlew :app:testReleaseUnitTest`（与 CI 门禁同款）
- 完整发版链路验证：`./gradlew :app:assembleRelease`

### 1.2 验证后自问：达到预期了吗？

四层走完后，主动想"有没有没想到的边界情况"，尤其这几类：

- **大文件**：特别长的文本、超大列表、超大图片，会不会卡、会不会崩？
- **慢网络 / 断网**：请求超时、网络断开时，App 会不会转圈卡死？
- **低电量 / 系统限制**：后台被回收、权限被收回，行为对不对？
- **快速连续操作**：狂点按钮、快速切换页面、重复提交，会不会重复执行或状态错乱？
- **空 / 异常数据**：没数据、出错返回、特别长的输入，会不会闪退？

### 1.3 验证不通过怎么办

- **编译报错**：就地修好再走下一层，不许带着报错往下写新功能。
- **测试失败**：先判断是"我改坏了"还是"测试本来就是坏的"。前者修代码，后者修测试，**不许随便删测试或加忽略**蒙混。
- **功能不符合预期**：先想清楚"预期到底是什么"，再动手，别凭感觉调。
- **发现新问题**：记下来，能顺手修就修；超出本次范围的记到 TODO 并告知用户，不瞒着。

### 1.4 验证通过后的输出标准

一次编程任务收尾，要能交出三样：
1. **四层验证全过**的代码；
2. 一句话说明"这次改了什么、为什么"（commit message 用）；
3. 若改了用户可见行为，CHANGELOG 有条目。

## 章节 2：CI 流程管理

CI（自动构建检查）不是"配好就不管"，它本身也要被审查和维护。

### 2.1 CI 配置变更要 review

- 改 CI 配置（`.github/workflows/*.yml`）和改业务代码一样，必须过本手册的验证清单：想清楚改了什么、会不会漏步骤、出问题怎么回退。
- CI 改动属于"构建链路改动"，按发版规范本身就该更谨慎。

### 2.2 每次发版前快速过一遍 CI 清单

打 Tag 前瞄一眼，确认该跑的都跑了：
- [ ] 该跑的步骤真的跑了吗？（没有被 `if` 条件意外跳过）
- [ ] Lint 真的执行了吗？（不是被缓存/异常跳过）
- [ ] 单元测试真的有用例吗？（不是 0 个用例假装绿）
- [ ] 产物校验（签名/大小/架构）都过了吗？

### 2.3 CI 失败要做根因分析

CI 红了不只是"重跑一遍"，必须回答：
- 为什么本地四层验证没发现这个问题？
- 哪一层验证漏了？以后怎么补上（加测试？加本地检查？）

### 2.4 当前 CI 自审查结果（v0.0.0.43 时盘点）

> 详细报告见对话记录；这里记录结论，作为后续优化基线。

**做得好的（已实现）**：Tag 触发与格式校验、拒绝预发布 Tag、完整 checkout、JDK17、Gradle 缓存、CHANGELOG 条目检查、版本号单调递增、包名不变校验、Lint baseline 门禁、自定义 lint 检查、单元测试、构建 Release、ABI 校验（仅 arm64）、自动上传 Release、正文生成、正式版不标记 prerelease、失败自动建 Issue 告警。

**待补的（缺口）**：
- ❌ 缺**显式签名校验**（构建后未用 `apksigner` 验证签名证书是否为官方那把）；
- ❌ 缺 **APK 大小阈值告警**（只打印大小，没有合理区间拦截）；
- ❌ 缺**构建成功通知**（失败有 Issue，成功无人知晓）；
- ⚠️ Release 正文由 git 提交记录生成，**不是直接读 CHANGELOG**，三处一致靠人工；
- ⚠️ 未校验"打出来的包 versionName 是否真的等于 Tag"。

> 这些缺口先记录，**经用户确认后再改 CI**，不在本次文档任务里动。

## 章节 3：功能设计流程

做新功能，**不要第一时间就给方案**。先理解场景、评估价值、学习借鉴、多方案对比，再出设计。

### 第一步：需求理解与拆解

- 把一句话需求拆成：用户怎么触发、系统做什么、最后呈现什么。
- 明确"必须有"和"以后再说"。
- **产出物**：需求说明（100 字内）+ 需求点清单。
- **验收标准**：用户读完能认同"对，我要的就是这个"。

### 第二步：想清楚"谁在用、在什么场景用"（用户场景）

- 谁会用这个功能？他在手机上、什么情况下、想用它解决什么？
- **产出物**：1-2 个典型使用场景描述。
- **验收标准**：能说清使用场景，而不是为做功能而做功能。

### 第三步：想清楚"不做会怎么样"（优先级）

- 不做这个功能，用户有没有别的替代办法？痛点有多大？
- **产出物**：一句话价值判断（为什么值得做）。
- **验收标准**：能解释优先级，不做也不至于误事就别急着做。

### 第四步：网上检索类似需求的设计方案（学习借鉴）

- 找同类产品/开源项目怎么做，重点看别人踩过的坑。
- **产出物**：2-3 个参考方案笔记（链接 + 做法 + 优缺点一句话）。
- **验收标准**：知道主流做法，而不是凭空发明。

### 第五步：分析现有方案优缺点

- 对比参考方案，结合本项目（手机端、AI Agent、内置终端）挑方向，优先复用已有轮子。
- **产出物**：优缺点对比 + 选定方向。
- **验收标准**：能解释"为什么选它、放弃了什么"。

### 第六步：加入创新思考

- 在选定方向上结合本项目特点改进，说清"比参考好在哪"。
- **产出物**：创新点列表（每条附理由）。
- **验收标准**：每条创新都有理由，不是为不同而不同。

### 第七步：输出至少 2-3 个方案对比

给三档方案，说清各自优缺点和成本，再推荐一个：
- **简单方案**：快、便宜，但能力有限；
- **平衡方案**：工作量适中，够用好用（通常推荐）；
- **激进方案**：一步到位，但工作量/风险大。

- **产出物**：方案对比表（成本 / 优缺点 / 推荐结论）。
- **验收标准**：用户能在"快但糙"和"慢但稳"间做知情选择。

### 第八步：输出设计规范

必须包含：**架构图**（几块怎么打交道）、**接口定义**（输入输出）、**数据模型**（存什么、存哪）、**流程图**（用户操作走一遍）。
- **产出物**：设计文档存 `docs/` 下。
- **验收标准**：照文档另一个人能直接动手写代码。

### 第九步：设计评审与迭代

- 给用户过目，按反馈修改，确认后再开工。
- **产出物**：确认后的设计终稿。
- **验收标准**：用户明确认可，开工后不大改方向。

### 第十步：MVP 定义（第一版做什么、不做什么）

- 明确第一版只做最小可用闭环，哪些明确不做、留到以后。
- **产出物**：MVP 范围清单（做 / 不做两列）。
- **验收标准**：开工前对"做到什么程度算完"有共识。

## 章节 4：Bug 修复流程

修 Bug 最忌讳"哪报错改哪"。要分级、查根因、管旧补丁、防复发。

### 第一步：接收 bug，复现问题

- 拿描述/日志/截图，先在本地按步骤稳定复现。复现不出来就继续找触发条件。
- **产出物**：可稳定复现的操作步骤。
- **验收标准**：每次都能触发。

### 第二步：bug 分级

| 级别 | 含义 | 处理要求 |
| --- | --- | --- |
| P0 | 崩溃 / 数据丢失 | 最高优先，立即修 |
| P1 | 核心功能用不了 | 本周期内修 |
| P2 | 体验不好 | 排期修 |
| P3 | 建议优化 | 空闲时做 |

- **产出物**：标明级别。
- **验收标准**：P0/P1 必须在报告里说清影响。

### 第三步：深度审计相关模块 + 关联模块

- 不只看报错文件，把该模块整体读一遍；再顺上下游查谁调用、共享组件会不会被牵连。
- **产出物**：模块工作原理理解 + 影响范围清单。
- **验收标准**：能讲清数据流，知道"动这里会碰到谁"。

### 第四步：找出相关旧补丁，逐个判断有效性

这个 bug 附近往往已经叠过旧补丁。对每个旧补丁判断属于哪一种：

| 状态 | 怎么处理 |
| --- | --- |
| 仍然有效且必要 | 保留，补注释写清原因和过期条件 |
| 有效但可加强 | 加强，和新补丁协同 |
| 被新补丁覆盖 | 清理掉 |
| 已经过时 | 删除 |
| 效果不好/有副作用 | 降级或回退 |
| 与新补丁冲突 | 二选一，留更优的 |
| 拿不准 | 标记待验证，加测试或日志观察 |

- **产出物**：旧补丁处理清单（每个补丁的处置）。
- **验收标准**：旧补丁去向都有结论，不留糊涂账。

### 第五步：定位核心原因（不是表象）

- 报错是症状，要问"为什么会走到这一步"。区分直接原因和根本原因。
- **产出物**：根因一句话。
- **验收标准**：修复冲着根因，不贴创可贴。

### 第六步：网上检索类似情况，学习借鉴

- 搜同类问题，看别人怎么定位、怎么修。
- **产出物**：参考方案笔记。
- **验收标准**：修复看过通行做法，不是闭门造车。

### 第七步：根据学习经验重新审计 bug

- 带着新认识回头再看代码，确认根因判断对不对（常常这步会发现更深一层原因）。
- **产出物**：二次确认后的根因结论。
- **验收标准**：根因经过"学习后再审"，有把握。

### 第八步：给出最优修复方案（含旧补丁处理）

- 给方案对比：各怎么做、改动多大、风险、回退方案；并写清旧补丁怎么处置。
- **产出物**：推荐方案 + 风险评估 + 回退方案。
- **验收标准**：用户能知情决策。

### 第九步：实施修复

- 新补丁 + 旧补丁处理放**同一个 commit**，避免中间态。
- **产出物**：修复代码。
- **验收标准**：一次提交同时解决新旧两处。

### 第十步：验证

- 原 bug 按复现步骤消失；旧补丁处置后相关功能正常；回归测试按影响范围跑一遍。
- **产出物**：验证记录。
- **验收标准**：问题消失且没引入新问题。

### 第十一步：给新补丁写过期条件

- 注释写清：什么时候加的、为什么、什么条件下可以删。
- **产出物**：补丁注释里的过期条件。
- **验收标准**：后人知道这补丁"哪天就可以拆了"。

### 第十二步：预防措施

- 以后怎么防类似 bug？加测试？加监控？改设计？
- **产出物**：预防措施清单。
- **验收标准**：同类问题下次能被自动发现。

### 第十三步：记录经验

- 补测试用例、更新文档，把经验沉淀下来。
- **产出物**：新测试 / 文档条目。
- **验收标准**：同类问题再犯会被自动挡住。

> 强调：第三步到第七步（深度审计 + 学习借鉴）**不能跳过**。只改报错那一行 = 下次还会炸。

## 章节 5：补丁管理三条铁律

代码里总有"临时修补"，管不好就变技术债。三条铁律必须守：

1. **补丁不能摞补丁**：发现补丁上面又打补丁，立刻停下来想——是不是该从根上重写，而不是继续糊。
2. **临时补丁必须有过期条件**：没有过期条件的临时补丁，就是永久补丁。注释里必须写"什么情况下可以删"。
3. **定期全量补丁审计**：每个大版本或每季度，扫描所有 `TODO` / `FIXME` / `HACK` / `WORKAROUND`，逐个判断还有效没效。

## 章节 6：代码注释规范

注释不是写流水账，是给"三个月后的自己"看的。

### 6.1 注释该回答的三个问题

1. 这段代码**做什么**？（代码本身已很清晰的，不用写）
2. **为什么要这么做**？（最关键——解释设计决策、为什么要绕路 workaround）
3. **什么条件下可以删除/修改**？（过期条件）

### 6.2 禁止阶段性词语

注释里不要出现"我们现在处于某阶段"这类过几个月就失效的话：
- ❌ 禁止：`P0` / `P1`、`T1`/`T2`、`阶段一/阶段二`、`rc34 修复`、`v0.0.0.43 新增` 这类带版本/阶段编号的说法。
- 阶段性信息放对地方：commit message、CHANGELOG、项目文档、任务列表。

### 6.3 例外（不算阶段性词语，是好注释）

- `// TODO: 当 XX 条件满足后重构` —— 写了过期条件，是好注释；
- `@Deprecated("将在 2.0 移除")` —— API 契约说明；
- `// 兼容 Android 10 以下` —— 描述代码行为；
- `// 大文件场景性能优化` —— 描述适用场景。

### 6.4 好注释 vs 坏注释

**坏注释（废话，重复代码）：**
```kotlin
// 设置 name 为 name
user.name = name
```

**坏注释（带阶段编号，过时即失效）：**
```kotlin
// v0.0.0.43 新增：修复 tree-sitter 高亮
```

**好注释（解释为什么 + 过期条件）：**
```kotlin
// 先写内存队列再批量刷盘，是因为直接写数据库在大文件导出时会卡住主线程；
// 等数据层换成异步写入管道后，这段缓冲逻辑可以删除。
```

## 章节 7：发版流程

发出去即终态（无灰度、无撤回），所以按门禁一步步来，发完还要盯。

### 7.1 发版前检查清单（打 Tag 之前）

- [ ] 代码冻结：本周期要发的改动全部合入 `main`，没有半拉子工程；
- [ ] 四层验证全过：编译、测试、功能实测、关联回归；
- [ ] `CHANGELOG.md` 已更新，条目符合规范；
- [ ] 版本号已确认：在上个正式版之上递增；
- [ ] 发版脚本/规范的最新改动已合入 `main`（CI 用的是 Tag 指向的代码）。

### 7.2 CI 构建流程（打 Tag 自动触发）

拉代码 → 配 JDK/SDK → 拒绝预发布 Tag → 校验版本号/包名/CHANGELOG → 单元测试 → Lint 门禁 → 构建 Release APK。

### 7.3 构建产物校验

- [ ] **签名**：是官方密钥签的正式包（不是 debug 包）；
- [ ] **大小**：APK 在合理区间（当前基线约 36MB），异常增大要告警；
- [ ] **架构**：只含 arm64-v8a，无多余架构；
- [ ] **功能**：装上真机，核心功能能正常用。

### 7.4 Release 发布流程

CI 自动建 Release 并传 APK → 人工补标题概括（≤20 字）和正文 → 三处内容一致（Release 正文 = CHANGELOG = 独立文档）。

### 7.5 发版后 24 小时监控

- 发版后头 24 小时重点盯：**崩溃报告、用户反馈**；
- 发现 P0 问题立即走下面的紧急通道。

### 7.6 快速回退

- **上一个版本 APK 始终保留**在 Release 页面，用户可手动降级安装；
- 原则：不删已发 Release，用新版本修问题，旧版作为退路。

### 7.7 紧急修复（hotfix）快速通道

- 紧急修复可跳过非必要步骤，但**核心验证（编译 + 测试 + 功能实测）一项不能省**；
- hotfix 版本号规则：在正式版后加一位，如 `v0.0.0.43.1`；
- hotfix 必须随后合回 `main`，避免主干丢失修复。

### 7.8 发版失败回退

- CI 失败：看失败步骤日志，修好后重新打 Tag 或重跑；
- 已发但有严重问题：打 hotfix 重发，旧 Release 标注已知问题。

## 章节 8：发版日志规范

发版日志**只写一层，面向用户**，不分技术版和用户版。技术细节放 commit message，CHANGELOG 只写用户能感知的。

### 8.1 格式

每条：`- **4-9字小标题**：20-40字简练说明`

### 8.2 分类顺序（固定）

新功能 → 改进 → 移除 → 修复 → 安全 → 已知问题（没有的分类整段省略）

### 8.3 语言要求

- **禁止 emoji**；
- **避免纯技术黑话**："重构""迁移""适配"这类词用户看不懂，换成用户能感知的描述；
  - 反例：`数据层 SQLDelight 迁移完成`
  - 正例：`会话列表打开更快了，滑动更跟手`
- 写"用户看到了什么变化"：更快了 / 支持更多了 / 修了某个问题。

### 8.4 好例子 vs 坏例子

**坏例子（技术黑话）：**
```
- **架构升级**：从 tree-sitter native 迁移到 sora-editor 纯 Java 方案。
```

**好例子（用户能懂）：**
```
- **代码高亮**：打开代码文件时高亮不卡顿，大文件也始终清晰。
```

模板见文末附录。

### 8.5 技术黑话对照表（必查）

下笔前逐词对照，命中左侧黑话一律改写成右侧用户向说法：

| 技术黑话（禁用） | 用户向措辞（推荐） |
|---|---|
| 重构 / 迁移 | 优化 / 升级 |
| 适配 XX 库 | 支持 XX |
| 引入 XX 框架 / XX 引擎 | 新增 XX 功能 |
| 移除 XX 依赖 | 精简了 XX，安装包更小 |
| 修复 NPE / 空指针 / 崩溃 | 修复了 XX 场景下闪退的问题 |
| 优化性能 / 内存 | 更快了 / 更省电了 |
| SQLDelight / Room / ORM | 数据库（不写具体库名） |
| OkHttpClient / Retrofit / 网络栈 | 网络请求（不写具体库名） |
| tree-sitter / sora-editor / grammar | 代码高亮引擎（不写具体库名） |
| Dagger / Hilt / DI | （用户无感知，不写） |

### 8.6 每条先过三问

写一条 CHANGELOG 前先自问：

1. **用户能感受到什么变化？**（更快 / 支持更多 / 修了某个问题）
2. **去掉具体库名、类名、版本号后，这句话还成立吗？**
3. **这是纯内部重构、用户完全无感吗？** —— 若是，**不写进 CHANGELOG**，只留在 commit message。

**坏例子**：`重构数据层，从 Room 迁移到 SQLDelight，删除 34 个 Entity 过渡层`
**好例子**：`优化数据存储，启动更快、占用更小`

**坏例子**：`引入两套 OkHttpClient，按模型路由到代理或直连`
**好例子**：`优化网络连接，海外模型访问更稳定`

## 章节 9：汇报规范

汇报是为了让对方快速做决定。分四种场景，各有固定套路。

### 9.1 问题汇报

顺序：**问题是什么 → 影响多大 → 怎么解决 → 什么时候好**。

### 9.2 成果汇报

顺序：**做了什么 → 效果怎么样（用数据）→ 下一步**。

### 9.3 进度汇报

顺序：**做到哪了 → 有没有卡住 → 预计什么时候完**。

### 9.4 决策汇报

顺序：**有几个选项 → 各自优缺点 → 我的建议**。

### 9.5 风险提前预警

- 发现潜在风险要**提前说**，不要等出问题再报；
- 哪怕只是"可能有问题"，也要先打个招呼。

### 9.6 通用要求

- 简洁、通俗；专业术语要么不用，用了就顺手解释；
- 用表格 / 对比 / 百分比呈现数据，不用大段文字；
- 禁止"大概""可能""差不多"这类模糊话，不确定就去查清。

### 9.7 好例子 vs 坏例子

**坏例子：**
> "今天看了下数据库，好像迁移哪里没弄好，查了挺久，大概快搞定了，可能明天好。"

**好例子：**
> "数据库升级崩溃已修复。根因：表结构复制不完整。现在升级零崩溃、数据 100% 保留，已通过测试，建议随下一版发布。"

## 章节 10：贯穿所有流程的规则

这几条不专属于某个流程，而是每件事都要守：

- **文档同步**：代码改了，文档必须同步改（README、用户指南、设计文档、SECURITY.md）。用户可见行为变了，说明文档不能落后。
- **知识沉淀**：问题解决后，经验必须记下来（写进文档或注释），别让同一个坑踩两次。
- **安全审查**：涉及密钥、权限、用户数据的功能，必须做安全审查再上线。
- **性能基准**：改性能相关代码，改前改后要有对比，不能越改越慢。
- **代码自审查**：提交前自己先 review 一遍，再交给 CI。

## 章节 11：质量门禁

什么情况必须"踩刹车"。

### 11.1 不能进入下一阶段

- 验证不通过（编译红、测试挂、功能不符合预期）；
- 设计不完整（缺架构图/流程/验收标准）；
- bug 未修复（根因没定位、修复没验证、回归没做）；
- CHANGELOG 缺失却要发版。

### 11.2 必须停下来报告

- CI 失败超过 2 次；
- 重大架构改动（动数据结构、包名、核心链路）；
- 安全问题（密钥、数据泄露、越权）；
- 修复方案与原计划偏差较大；
- 自己拿不准、有风险的事。

### 11.3 并行 vs 串行

- **可并行**：互不影响的独立任务；查资料与写文档可同时推进。
- **必须串行**：发版相关一切；改同一份文件；涉及线上数据的操作；Bug 修复未验证前不叠加新改动。
- **铁律**：**发版期间，任何无关提交都不许 push 到正在发版的分支/Tag 上**，避免干扰发版。

## 附录：CHANGELOG 标准模板

每个新版本放 `docs/Version Log/CHANGELOG.md` 顶部：

```markdown
## [0.0.0.44] - 2026-10-05

<100字以内简介：这个版本用户能感知到什么变化>

### 新功能

- **4到9字小标题**：20到40字简练说明，写用户能看到的变化。

### 改进

- **小标题**：用户能感知的优化，例如"启动更快了"。

### 移除

- **小标题**：去掉了什么，为什么。

### 修复

- **小标题**：原来什么现象，现在好了。

### 安全

- **小标题**：安全相关增强。

### 已知问题

- 还存在的问题；没有就写"无"。
```

要求：分类顺序固定、每条 `**4-9字小标题**：20-40字`、禁止 emoji、写用户话不写技术词、每条一个变更。
